Visão geral

Como as peças se ligam. O analista só conversa com o agente e acompanha o pull request no navegador.

Versão interativa, com busca, caminho entre nós e exportação: diagrama/docqui-copilot.html, no pacote.

O analista faz

  • Conversa com o agente e aprova cada artefato antes da gravação.
  • Acompanha o PR no navegador e pede a revisão.

Roda sozinho

  • O workflow regenera-gerados grava o espelho do INDEX, o diagrama ER, os dicionários e o HTML da AIMM.
  • O spec-guard e o gate-check conferem cada push.
  • O Pages publica a prévia da branch.

Credenciais

  • O agente grava com a conta do próprio analista (OAuth).
  • O workflow grava com o GitHub App docqui-bot.
  • A main só recebe PR aprovado.

1. GitHub: organização

Feito uma vez, pelo dono da organização. A interface do GitHub é em inglês; os nomes de botão aparecem como estão na tela.

  1. É a "conta" que o workflow usa para gravar os arquivos gerados. Precisa ser um App, e não o token padrão do Actions: o commit feito com o token padrão não dispara os checks, e o PR ficaria esperando para sempre.

    1. Na página da organização, clique em Settings. No fim do menu da esquerda, abra Developer settings → GitHub Apps → New GitHub App. Numa conta pessoal, o caminho começa pelo seu avatar → Settings.
    2. GitHub App name: docqui-bot-<org> (o nome precisa ser único em todo o GitHub).
    3. Homepage URL: o endereço da organização, por exemplo https://github.com/<org>.
    4. Em Webhook, desmarque Active.
    5. Em Permissions → Repository permissions, ponha Contents em Read and write. Não mexa nas outras.
    6. Em Where can this GitHub App be installed?, escolha Only on this account.
    7. Clique em Create GitHub App. Na página que abre, em About, anote o App ID: só números. Não confunda com o Client ID, logo abaixo, que começa com Iv.
    8. No menu da esquerda do App, abra Credentials → aba Key pairs e clique em Generate a private key. Um arquivo .pem é baixado. Guarde-o com cuidado: é uma senha. A aba Client secrets é de login por OAuth e não entra aqui. Em telas mais antigas do GitHub, as chaves ficam no fim da página principal do App, em Private keys.
    1. Na página do App, menu da esquerda, clique em Install App → Install ao lado da organização.
    2. Escolha Only select repositories e marque os repositórios de documentação (os <sistema>-doc). Clique em Install.

    Repositório novo de documentação? Volte aqui e acrescente-o à lista.

    1. Em Settings da organização → Secrets and variables → Actions → New organization secret.
    2. Name: DOCQUI_APP_ID. Secret: o número do App ID. Em Repository access, escolha Selected repositories e marque os repositórios de documentação. Salve.
    3. Repita com Name DOCQUI_APP_PRIVATE_KEY. Em Secret, abra o arquivo .pem num editor de texto e cole o conteúdo inteiro, inclusive as linhas -----BEGIN e -----END.
    Sem acesso aos segredos da organização?Crie os mesmos dois segredos em cada repositório: Settings do repositório → Secrets and variables → Actions → New repository secret.

  4. É o que permite que cada analista entre no GitHub com a própria conta quando o agente for gravar. Assim, cada commit sai no nome de quem trabalhou, e ninguém consegue aprovar o próprio PR.

    1. Em Settings da organização → Developer settings → OAuth Apps → New OAuth App.
    2. Application name: Docqui Caixa no Copilot Studio. Homepage URL: o endereço da organização.
    3. Authorization callback URL: por enquanto, https://localhost. No passo 3.3, o Copilot Studio mostra o endereço certo, e você volta aqui para trocar.
    4. Clique em Register application. Anote o Client ID, clique em Generate a new client secret e anote o segredo: ele só aparece uma vez.
    Organização com acesso de apps restritoEm Settings → Third-party access → OAuth app policy, aprove este app. Sem isso, o agente não enxerga os repositórios da organização.

  5. O agente lê o método — prompts, skills e templates — do repositório do engine, na branch main, e não de cada repositório de documentação. Um só lugar para atualizar.

    1. Dê aos analistas, pelo grupo ou time deles, ao menos acesso de leitura ao repositório do engine. É o que o agente usa para ler o método e, na retro, para abrir issue.
    2. No repositório do engine, abra Issues → Labels → New label, crie o rótulo retro e salve.
    A main do engine vale para todas as instâncias na horaO que entra na main passa a ser o método de todo agente, em todos os sistemas, na próxima conversa. Release que pede migração nas instâncias (como a 7.0.0, que trocou os nomes dos níveis) só entra na main com as instâncias migradas.

2. Cada repositório de documentação

Repita esta parte em cada repositório <sistema>-doc que o agente vai atender.

  1. Abra o repositório no navegador e confira que tudo abaixo existe. Quase tudo já vem da criação da instância (init-instance) e da sincronização com o engine (sync-instance), feitas por quem mantém o engine. O que está em amarelo você adiciona com este pacote.

  2. A cada gravação do agente numa branch de ticket ou de sprint, ele regenera os arquivos derivados e os grava na mesma branch. Sem ele, todo push fica vermelho no spec-guard.

    1. Na página do repositório, clique em Add file → Create new file.
    2. No campo do nome, digite .github/workflows/regenera-gerados.yml (as barras criam as pastas).
    3. Copie o conteúdo abaixo e cole na área de texto.
    4. Clique em Commit changes…, mantenha Commit directly to the main branch e confirme. Se a main já estiver protegida, escolha criar uma branch e abra o PR.
    .github/workflows/regenera-gerados.yml
    # regenera-gerados.yml — regenera os arquivos derivados na branch do ticket ou da sprint.
#
# COMO USAR NA INSTÂNCIA: copie para `.github/workflows/regenera-gerados.yml` e crie os
# segredos DOCQUI_APP_ID e DOCQUI_APP_PRIVATE_KEY (o GitHub App descrito no guia).
#
# Para quê: quem grava a especificação pelo agente do Copilot Studio não roda scripts. Sem
# este workflow, o espelho da esteira no modules/INDEX.md, o diagrama ER, o índice de uso
# dos dicionários e o HTML das AIMMs ficam para trás, e o spec-guard e o gate-check
# reprovam todo push. A cada push na branch, ele roda o mesmo comando que a pessoa rodaria
# (`node scripts/atualiza-pages.mjs --com-dicionarios`) e grava o resultado na branch:
#   • um commit por AIMM que a branch alterou, só com o HTML dela e com a chave da AIMM no
#     assunto — o HTML mora em analise-impacto/, que é spec, e o valida-commits-ticket só
#     aceita spec num commit que cite a chave;
#   • um commit "[gerado]" com o resto (espelho da esteira, diagrama ER, dicionários,
#     repos/INDEX.md e os arquivos do site). O assunto abre com a unidade de entrega da
#     branch: a chave da história em historia/<CHAVE>, porque tudo o que muda nela decorre
#     daquele ticket; o id da sprint em sprint/<id>, porque o diagrama da sprint é a soma
#     dos tickets dela e não pode levar a chave de um só (o reverte-ticket reverte os commits
#     que citam a chave do ticket). Em checkpoint/, sem chave. O valida-commits-ticket aceita
#     o [gerado] com ou sem chave: dele, só confere que o commit toca apenas arquivo gerado.
# O HTML das AIMMs que a branch não alterou não entra: o commit citaria a chave de outro
# ticket. Arquivo de spec fora dessa lista que mudar faz o workflow parar sem gravar nada.
#
# O push usa o token do GitHub App, não o GITHUB_TOKEN: push feito com o GITHUB_TOKEN não
# dispara os outros workflows, e o PR ficaria esperando para sempre os checks do commit
# novo. O commit do App dispara este workflow de novo; a condição `if` do job pula essa
# execução pelo autor do commit (`docqui-bot`), e não pela mensagem, que muda de um commit
# para outro. A concorrência não cancela a execução em andamento: com `cancel-in-progress`,
# a execução que o próprio commit do App dispara cancelava a que acabara de gravá-lo, e o
# trabalho feito aparecia como cancelado. Push novo durante a regeneração espera a vez; o
# laço de tentativas abaixo cobre o caso de a branch mudar no meio.

name: Regenera arquivos gerados

on:
  push:
    branches: ["historia/**", "sprint/**", "checkpoint/**"]
    paths: ["modules/**", "global/**", "analise-impacto/**", "repos/**"]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: regenera-${{ github.ref }}
  cancel-in-progress: false

jobs:
  regenera:
    # só em branch de entrega (nunca na main, nem pelo botão Run workflow) e não no commit do próprio workflow
    if: >-
      (startsWith(github.ref_name, 'historia/') || startsWith(github.ref_name, 'sprint/') || startsWith(github.ref_name, 'checkpoint/')) &&
      github.event.head_commit.author.name != 'docqui-bot'
    runs-on: ubuntu-latest
    steps:
      - name: Token do GitHub App
        id: app
        uses: actions/create-github-app-token@v1
        with:
          app-id: ${{ secrets.DOCQUI_APP_ID }}
          private-key: ${{ secrets.DOCQUI_APP_PRIVATE_KEY }}

      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          token: ${{ steps.app.outputs.token }}

      - uses: actions/setup-node@v4
        with: { node-version: "20" }

      - uses: actions/setup-python@v5
        with: { python-version: "3.x" }

      - name: Dependências
        run: pip install pyyaml

      - name: Regenerar e gravar na branch
        env:
          BRANCH: ${{ github.ref_name }}
        run: |
          set -euo pipefail
          git config user.name "docqui-bot"
          git config user.email "docqui-bot@users.noreply.github.com"
          GERADO='^(modules/INDEX\.md|global/DIAGRAMA-ER\.md|global/[A-Z-]+-DICTIONARY\.md)$'
          SPEC='^(modules|global|qa|prototypes|analise-impacto)/'
          case "$BRANCH" in
            historia/*) UNIDADE="${BRANCH#historia/}: " ;;
            sprint/*) UNIDADE="${BRANCH#sprint/}: " ;;
            *) UNIDADE="" ;;
          esac

          for tentativa in 1 2 3; do
            git fetch -q origin "$BRANCH" main
            git reset -q --hard "origin/$BRANCH"
            git clean -qfd

            node scripts/atualiza-pages.mjs --com-dicionarios

            # 1. O HTML de cada AIMM que a branch alterou, com a chave da AIMM.
            base=$(git merge-base origin/main HEAD)
            for md in $(git diff --name-only --diff-filter=AMR "$base" HEAD -- 'analise-impacto/AIMM-*.md' 'analise-impacto/AIM-*.md'); do
              html="${md%.md}.html"
              [ -f "$html" ] || continue
              git add -- "$html"
              if ! git diff --cached --quiet; then
                chave=$(basename "$md" .md); chave=${chave#AIMM-}; chave=${chave#AIM-}
                git commit -q -m "$chave: HTML da AIMM regenerado pelo workflow"
              fi
            done

            # O HTML das demais AIMMs fica como está na branch.
            git checkout -q -- analise-impacto/
            git clean -qf -- analise-impacto/

            # 2. O resto num commit [gerado], desde que só toque o que o valida-commits-ticket aceita.
            git add -A
            fora=$(git diff --cached --name-only | grep -E "$SPEC" | grep -Ev "$GERADO" || true)
            if [ -n "$fora" ]; then
              echo "::error::A regeneração alterou arquivos de spec que não são gerados — nada foi gravado:"
              echo "$fora"
              exit 1
            fi
            if ! git diff --cached --quiet; then
              git commit -q -m "${UNIDADE}[gerado] artefatos derivados regenerados pelo workflow"
            fi

            if [ "$(git rev-list --count "origin/$BRANCH..HEAD")" = 0 ]; then
              echo "Nada a regenerar: os arquivos gerados já estão em dia."
              exit 0
            fi
            git log --oneline "origin/$BRANCH..HEAD"
            if git push -q origin "HEAD:$BRANCH"; then exit 0; fi
            echo "A branch recebeu outro push durante a regeneração; refazendo ($tentativa/3)."
          done
          echo "::error::A branch mudou três vezes durante a regeneração. Rode o workflow de novo em Actions."
          exit 1

  3. Abra .github/CODEOWNERS, clique no lápis (Edit this file) e troque cada @org/… pelo time real: PO para /modules/, DBA para o modelo de dados, e assim por diante. É o que faz o GitHub chamar a pessoa certa para revisar.

    1. Crie uma branch de teste: no seletor de branch (o botão com main, acima da lista de arquivos), digite historia/STRY0000000 e clique em Create branch.
    2. Nessa branch, edite um arquivo de global/data-models/, por exemplo acrescentando uma linha de atributo numa entidade, com a mensagem de commit STRY0000000: teste do workflow.
    3. Abra a aba Actions. O workflow Regenera arquivos gerados tem de rodar e terminar com ✓ verde.
    4. Volte à branch e abra commits: tem de aparecer um commit do docqui-bot com [gerado] na mensagem.
    5. Abra um PR da branch para a main e confira que os checks rodam sobre o commit do docqui-bot. Depois, feche o PR sem merge e apague a branch.

    O teste também faz os checks aparecerem na lista do passo seguinte: o GitHub só oferece um check para exigir depois que ele rodou ao menos uma vez.

    1. Settings do repositório → Branches → Add classic branch protection rule.
    2. Branch name pattern: main.
    3. Marque Require a pull request before merging, Require approvals (1) e Require review from Code Owners.
    4. Marque Require status checks to pass before merging e Require branches to be up to date before merging. Na busca de checks, adicione Esteira de gates — check, estrutura, rastreabilidade e entrega. Os três últimos são do spec-guard; o entrega é o que barra na main uma história sem AIMM concluída.
    5. Marque Do not allow bypassing the above settings e clique em Create.
    Por que dá para exigir os checks do spec-guardDesde a 8.2.2, o spec-guard roda em todo PR, inclusive nos que não mexem na especificação, como o da retro. Num PR que não é de uma branch historia/ ou sprint/, o entrega é pulado, e o GitHub conta check pulado como aprovado. Repositório com um spec-guard.yml anterior à 8.2.2: apague dele a linha paths: logo abaixo de pull_request:, senão os PRs que não mexem na especificação ficam esperando para sempre esses checks.
    1. Settings → Pages → em Source, escolha GitHub Actions.
    2. Settings → Environments → github-pages → Deployment branches and tags → Selected branches and tags. Adicione main, historia/* e sprint/*.

    Cada branch de ticket ganha uma prévia do site, com o HTML da AIMM, para o PO e o revisor lerem sem abrir o código.

    # Papel
Você conduz sessões de especificação de requisitos com o método Docqui Caixa sobre o repositório de documentação de um sistema (a "instância") no GitHub. Você não guarda o método de memória: ele está no repositório do engine, <REPO_ENGINE>, na branch main, e você o lê pela ferramenta do GitHub antes de agir.
Dois repositórios: todo caminho do método (engine/..., .claude/skills/..., VERSION, e os arquivos do engine que as skills e os prompts citam) você lê do <REPO_ENGINE>, branch main; global/, modules/, analise-impacto/, prototypes/, qa/, repos/, CLAUDE.md e .github/ são da instância.

# 1. Repositório da conversa (sempre o primeiro passo)
1. Pergunte qual sistema a pessoa vai documentar. Se ela não souber o repositório, liste os repositórios da organização <ORG> cujo nome termina em "-doc" e peça que escolha um.
2. Leia o "global/MASTER.md" desse repositório e o "VERSION" do <REPO_ENGINE> e responda: "Sistema: <Sigla> — <Nome> (<owner>/<repo>), Docqui <VERSION>, perfil <Perfil>, cadência <Cadência>. É este?". Aguarde a confirmação.
3. Repositório sem "global/MASTER.md" não é instância do Docqui: diga isso e peça outro.
4. Confirmado, use esse owner/repo em TODA chamada da conversa. Nunca leia nem grave em outro repositório, exceto o <REPO_ENGINE>: dele você lê o método e, na retro, abre issue; nunca grava nele. Para trocar de sistema, a pessoa abre outra conversa.

# 2. Contexto e método
Após a confirmação, leia "global/N0_PRODUCT_VISION.md" e "modules/INDEX.md" e apresente os domínios e Agrupamentos Funcionais já documentados. Leia também a seção "Regras da instância" do CLAUDE.md da raiz e siga-a. Os demais arquivos você lê sob demanda; arquivo da instância se lê, não se pede para colar.
Leia a skill INTEIRA antes de conduzir, e siga-a como regra da sessão:
- fechar a AIMM de um ticket já entregue ou escrever a AIMM da sprint: ".claude/skills/analise-impacto/SKILL.md";
- todo o resto: ".claude/skills/analista-requisitos/SKILL.md".
Leia os arquivos de "references/" da skill quando ela mandar. Se uma leitura falhar ou vier cortada, pare e avise; não conduza de memória.

# 3. Menu
Leia "engine/prompts/PROMPT_MENU.md" e apresente o menu do perfil do MASTER (sem perfil = requisitos). Escolhida a opção, abra o arquivo INTEIRO do prompt indicado na tabela de execução do PROMPT_MENU e siga o roteiro do começo ao fim.

# 4. Scripts que você não roda
Aqui nenhum script roda. Quando a skill ou o prompt mandar rodar:
- preflight-spec.mjs: leia o N0, o modules/INDEX.md e o N1/N2 pertinentes e apresente o bloco "Contexto verificado" (o que existe, IDs tomados, próximo NN livre, canônicos a referenciar).
- monta-contexto.mjs <ID>: leia o N3 e só os trechos dos globais que ele cita; o que ele cita e não existe vai como ❓.
- ids-n3.mjs: siga "engine/N3-IDS.md"; proponha os IDs pela jornada do N2, depois do maior reservado em docqui:n3-ids, sem preencher lacunas; confirmado, grave no N2 o que o N3-IDS.md manda o script gravar. ID já usado nunca muda.
- validadores (validate-doc, valida-*, validate-impact, verifica-texto-corrido): confira você mesmo antes de gravar; depois do push, leia os checks do PR.
- atualiza-pages, gera-*, generate-*, gates.py promote: não rode nem imite. O workflow "Regenera arquivos gerados" grava esses arquivos na branch, em commits do docqui-bot. Não edite à mão: global/DIAGRAMA-ER.md, o HTML das AIMMs, assets/ e o trecho do modules/INDEX.md entre <!-- GATES:INICIO --> e <!-- GATES:FIM -->.
- git diff do "antes": leia o arquivo na main (antes) e na branch (depois) e compare.
Nunca diga que rodou um script.

# 5. Gravação no GitHub
- Nunca grave na main. Siga a Cadência do MASTER e "Onde a AIMM vive" do PROMPT_AIMM.md: história, branch historia/<CHAVE> criada da main ao abrir a AIMM; sprint, branch sprint/<id>.
- Na instância, grave só em modules/, global/, analise-impacto/, prototypes/, qa/ e repos/ (o CLAUDE.md da raiz, só pela retro); scripts/, .github/ e, se existirem, engine/ e .claude/ são somente leitura.
- Releia o arquivo na branch logo antes de alterá-lo: o workflow pode tê-lo mudado.
- Antes de cada gravação, mostre repositório, branch, arquivos e mensagem do commit, e aguarde o "sim". Arquivos do mesmo passo vão num commit só.
- O assunto do commit começa pela chave do ticket da branch e não cita outra: "STRY0013120: especifica Calcular Frete (N3)".
- Carimbo: a primeira linha de todo artefato gerado ou atualizado é <!-- docqui: <VERSION do engine> | prompt: <PROMPT_ID> | atualizado: <data> -->. A data vem do tópico "Data de hoje"; se ele falhar, pergunte a data; nunca invente. Em atualização, reescreva a linha.
- Texto corrido: cada parágrafo numa linha só.

# 6. PR e checks
Depois do primeiro push, abra o PR em rascunho (draft) da branch para a main, com a descrição no modelo ".github/pull_request_template.md". A cada push seu, espere o commit do docqui-bot e leia os checks do PR. Check vermelho: mostre o erro, corrija e grave de novo. Não diga que um artefato está concluído com check vermelho ou rodando. Só tire o PR do rascunho quando a pessoa pedir.

# 7. Regras que mais escapam (a fonte é a skill)
- Toda resposta começa com [Estado: NOME]. Uma pergunta por mensagem. Nunca pule estado. Um artefato por vez, com aprovação explícita antes de gravar.
- Modo PO: só linguagem de negócio, sem endpoint, enum, FK, JSON, HTTP, tabela, coluna.
- Definição de banco vive só em global/data-models/; o N3 cita por referência e usa Label PO.
- Cruze com os dicionários antes de perguntar. Erro e mensagem novos: proponha com ⚠️ e aguarde aprovação.
- Regra de negócio é invariante com **RN-NN** e cenário @RN-NN; a reação vai para Cenários.
- Não conte Pontos de Função; funcionalidade nova ou alterada deixa contagem.pendente: true.
- Não invente regra: lacuna vira ⚠️ e pergunta. Cite funcionalidade como "ID — Nome".
- Você documenta o sistema-alvo, nunca o framework: pedido de novo prompt ou template, recuse.
- Não aprove PR, não faça merge, não force push, não apague branch.

# 8. Como trabalhar
1. Pense antes de especificar. Não assuma: declare as suposições com ⚠️. Se o pedido tem mais de uma leitura, apresente as leituras e pergunte; não escolha em silêncio. Se há caminho mais simples (alterar o que existe em vez de criar), diga. Se algo não está claro, pare, diga o que está confuso e pergunte.
2. Simplicidade primeiro. Especifique só o que o ticket ou a pessoa pediu: nenhuma funcionalidade, regra, campo ou cenário especulativo, nenhuma "flexibilidade" que ninguém pediu, nenhum cenário para situação impossível. Se o texto pode ter metade do tamanho sem perder nada, reescreva.
3. Mudanças cirúrgicas. Altere só o que o pedido exige. Não "melhore" seções vizinhas, redação ou formatação; siga o estilo do artefato. Problema fora do pedido: mencione, não corrija. O Changelog é histórico: acrescente uma linha, nunca reescreva as antigas. Ao regravar um arquivo, parta da versão atual da branch e confira que todos os cabeçalhos ## de antes continuam lá. Mudança que toca vários artefatos: mostre o primeiro e só siga com o "sim".

Por que é assim

As escolhas deste desenho, para quem for manter ou questionar.

O HTML da AIMM é gerado pelo workflow e versionado na branch

O HTML da AIMM sai do .md por um script, e o agente não roda scripts. Havia dois caminhos: gerar o HTML só na publicação do site, sem guardá-lo no repositório, ou gerá-lo no workflow e guardá-lo na branch.

A escolha foi guardá-lo, num commit por AIMM com a chave dela. Isso mantém o contrato atual do engine, que entrega o .md e o .html lado a lado, sem mudar nenhum script. O HTML aparece no PR e na prévia do site, e o link que a equipe de métricas usa não muda. Ele não pode ir no commit [gerado]: mora em analise-impacto/, que é especificação, e o check de commits reprovaria. Gerar só na publicação é mais limpo, porque não deixa arquivo derivado no repositório, mas exige mudar o engine; fica como evolução.

Um agente para todos os repositórios

O agente pergunta, no começo de cada conversa, qual sistema documentar. Um agente por repositório seria um agente para publicar e atualizar por sistema, a cada versão do engine. O acesso fica com o GitHub: cada analista só alcança os repositórios a que já tem acesso.

A especificação num agente só, com o Retro à parte

Um roteiro de especificação tem muitas mensagens, e trocar de agente no meio pode perder o estado da conversa. Por isso as duas skills ficam no mesmo agente, que lê a certa para cada pedido. O Retro é um agente filho porque acontece no fim, quando trocar de agente não interrompe nada, e porque as instruções do principal já estão perto do limite de caracteres. O desenho com dois agentes filhos de especificação está guardado em agentes/alternativa-child-agents/.

O método vem da main do engine, não de cada repositório

Os prompts, as skills e os templates ficam num lugar só: o agente os lê do repositório do engine, na main. Atualizar o método é uma release no engine, sem replicar nada nos repositórios dos sistemas. O preço é que toda instância anda junto com a main: uma release que exige migração só entra quando as instâncias estiverem migradas. Os scripts da CI continuam em cada repositório, levados pelo sync-instance, porque os workflows rodam a partir da instância; centralizá-los com workflows reutilizáveis fica para depois.

Os prompts não vão como "conhecimento"

O conhecimento do Copilot Studio busca trechos. Os prompts do método são roteiros com estados, e o agente que recebe só um pedaço pula etapas. Por isso o agente abre o arquivo inteiro pela ferramenta do GitHub.

A retro não edita o engine

No repositório do sistema, engine/, scripts/ e .claude/ são cópias do engine, que a próxima sincronização sobrescreve. O que vale para todos vira issue no engine, e quem o mantém aplica numa versão nova, com a /retro do Claude Code. O que vale só para um sistema vai para o CLAUDE.md dele, por PR, e o agente o lê no começo de toda conversa.

Glossário

Instância
O repositório de documentação de um sistema, como loja-acme-doc.
Engine
O repositório do método Docqui Caixa: prompts, templates, skills e scripts.
Branch
Uma linha de trabalho separada da versão oficial. Cada ticket tem a sua, historia/<CHAVE>.
Pull request (PR)
O pedido para levar uma branch para a main, com a revisão. "Rascunho" (draft) ainda não pede revisão.
Check
Uma conferência automática que roda a cada gravação; fica verde ou vermelha.
Workflow
Uma automação do GitHub Actions, descrita num arquivo .yml em .github/workflows/.
GitHub App
Uma conta de automação com permissões limitadas. Aqui, o docqui-bot, que grava os arquivos gerados.
OAuth
O login que deixa o agente agir com a conta de cada analista, sem guardar senha.
MCP
O protocolo pelo qual o agente usa ferramentas externas; aqui, o GitHub.
Segredo
Um valor sigiloso guardado no GitHub, que o workflow lê sem mostrar.
AIMM
A Análise de Impacto de Mudança para Manutenção: um arquivo por ticket, em analise-impacto/.
Retro
O registro, no fim de uma conversa, do que ela ensinou, no lugar em que o agente vai ler da próxima vez.
